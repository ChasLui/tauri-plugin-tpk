## 0. 以终为始：上线后系统长什么样

用户安装的是「壳 + 保底内容」。之后绝大多数内容更新只下载 `.tpk`，不必替换可执行文件。

系统必须同时具备：

1. 多层叠加：Embedded → Base → Patches → DLC → Mods〔未实现〕（安装包内的 seed 只是首启时 base 的来源）\
2. 文件级增量 + 大文件二进制 delta + 删除墓碑\
3. 签名清单 + 包签名 + key epoch 轮出 + 防重放 + `min_shell`\
4. 三态指针：staged / booting / committed，坏包永不砖机\
5. 渠道、按设备百分比灰度、强制壳升级\
6. 官方 `tauri-plugin-updater` 只负责原生壳（仅桌面）\
7. 同一套格式用于桌面与移动；WebView origin 永不改变\
8. Rust 与 WebView 走同一 resolver 读资源\

**磁盘格式、清单字段、命令名、状态机** 按本文冻结。

## 1. 角色与数据流

```
构建机
  dist/
       │  tpk pack（含 --parent 生成 delta 与墓碑）/ tpk channel / tpk verify
       ▼
  artifacts/
    core-20260901120000.tpk
    core-20260908150000.tpk
    latest.json
    latest.json.minisig
       │  上传 CDN
       ▼
客户端
  generate_context!() → attach(&mut ctx)        换 Assets，不解析路径
  Builder::build() 末尾，插件 setup             Store::open → seed → boot() → 建索引 → OnceLock 装入
  创建窗口 → WebView 以 tauri:// 读叠加后的文件
  前端显式 check() → download()                 download 内完成 stage 与 delta 物化
  前端首屏就绪 → notify_ready() → commit
  壳过旧 → shell_required，由宿主引导升壳
```

两条更新通道永远分开：

| 通道 | 产物 | 触发 |
|---|---|---|
| Shell | 官方 updater 整包（桌面）/ 应用商店（移动） | Rust、权限、插件、sidecar、WebView 能力、CSP 策略结构变化 |
| Content | `.tpk` + 渠道清单 | JS/CSS/HTML、文案、图片、关卡、配置、可热替换资源 |

前端禁止配置更新 URL 与公钥。


## 3. 包格式 TPK/1（冻结）

### 3.1 容器

- 外层：ZIP。读端接受 stored 与 deflate；`tpk pack` 固定输出 stored，压缩在 blob 层做，便于随机读
- 中央目录必须存在；ZIP 注释必须为空；条目数 ≤ 65536；条目名不得重复
- 验签前读取有上限：`tpk-manifest.json` ≤ 4 MiB，`tpk-manifest.json.minisig` ≤ 64 KiB；超出 → `E_SPEC`
- 条目名只允许以下形态：

```
tpk-manifest.json
tpk-manifest.json.minisig      # 必需：内嵌清单签名
blobs/<blob_sha256>            # encoding = identity
blobs/<blob_sha256>.zst        # encoding = zstd | zstd+bsdiff
```

- `<blob_sha256>` 是 blob 字节（压缩后、落在 ZIP 里的字节）的 sha256，小写 hex
- 清单引用的 blob 必须存在；不得存在未被引用的 blob
- 文件名魔法：扩展名 `.tpk`
- MIME：`application/vnd.tauri.tpk+zip`

不使用自定义二进制头作为唯一真相，ZIP+JSON 便于检视与跨语言；校验以清单为准。

### 3.2 `tpk-manifest.json`

```json
{
  "spec": "tpk/1",
  "kind": "base | patch | dlc | mod",
  "id": "core",
  "version": "1.0.3",
  "version_code": 20260908150000,
  "min_shell": "2.3.0",
  "max_shell": null,
  "parent": {
    "id": "core",
    "version": "1.0.0",
    "version_code": 20260901120000,
    "manifest_sha256": "hex64"
  },
  "created_at": "2026-09-08T15:00:00Z",
  "channel": "stable",
  "policies": {
    "can_override": ["**"],
    "cannot_override": [],
    "trusted": true
  },
  "entries": [
    {
      "path": "/index.html",
      "op": "full",
      "size": 4096,
      "sha256": "hex64",
      "blob": "blobs/<blob_sha256>.zst",
      "blob_sha256": "hex64",
      "blob_size": 1532,
      "encoding": "zstd"
    },
    {
      "path": "/assets/big.bin",
      "op": "delta",
      "size": 1048576,
      "sha256": "hex64",
      "blob": "blobs/<blob_sha256>.zst",
      "blob_sha256": "hex64",
      "blob_size": 20480,
      "encoding": "zstd+bsdiff",
      "delta_base_sha256": "hex64"
    },
    {
      "path": "/old.css",
      "op": "delete"
    }
  ]
}
```

字段规则：

- `spec` 必须为 `tpk/1`。未知 spec 拒绝加载。
- `kind` 四选一，禁止扩展时改旧包含义；新 kind 必须升 spec。
- `id`：`[a-z0-9][a-z0-9-]{0,62}`。
- `version`：SemVer。`version_code`：非 0 的单调正整数，比较只用它；推荐 UTC `YYYYMMDDHHMMSS`（§17.4）。
- `created_at`：RFC 3339。
- `min_shell` / `max_shell`：严格 SemVer（`MAJOR.MINOR.PATCH[-pre][+build]`，无前导零）或 `null`；两者都给出时 `min_shell ≤ max_shell`。
- `parent`：`base` 必须为 `null`；`patch` 必须存在；`dlc`/`mod` 可空。存在时 `parent.id == id` 且 `parent.version_code < version_code`。
- `policies`：三个字段必须被解析。`can_override` 必须为 `["**"]`、`cannot_override` 必须为 `[]`，其他值 → `E_POLICY`；`kind = mod` 必须 `trusted = false`。
- `path`：POSIX，必须以 `/` 开头，UTF-8 NFC，禁止 `\`、`.`、`..`、空段、盘符。文件名必须带扩展名（由 `tpk pack` 强制，§10.3）。
- `op`：`full | delta | delete`。
- `op != delete` 的 entry 必须带 `size`、`sha256`、`blob`、`blob_sha256`（ZIP 内 blob 字节的哈希）、`blob_size`（ZIP 内 blob 字节数）、`encoding`；`blob` 名中的 hex 段必须等于 `blob_sha256`。`op = delete` 禁止带这些字段。
- `op = delta` 必须带 `delta_base_sha256`，`encoding` 必须为 `zstd+bsdiff`；`op = full` 禁止带 `delta_base_sha256`，`encoding` 不得为 `zstd+bsdiff`。
- 只有 `kind = patch` 的清单可含 `op = delta`；其他 kind 含 delta entry → `E_SPEC`。`dlc`/`mod` 即使带 `parent` 也不得含 delta（stage 时它们替换同 `id` 的层，delta 的 base 已不存在）。
- `encoding`：`identity | zstd | zstd+bsdiff`。
- 同一 path 在同一清单中只能出现一次。
- `entries` 非空，且必须按 path 字典序排列。

### 3.3 签名

- 算法：minisign（Ed25519）
- 清单签名对象：`tpk-manifest.json` 的原样字节（不转码、不重排）；签名内嵌为 `tpk-manifest.json.minisig`
- 整包另算 `sha256(tpk-file)` 写入渠道清单
- 信任公钥写在原生配置 `plugins.tpk.pubkeys`，形如 `[{key, epoch}]`；`epoch` 为正整数，缺省 1
- 客户端持久化单调下限 `min_key_epoch`（缺省 1，存于 `state.json`）：
  - 渠道清单：只用 `epoch == key_epoch` 的钥验签，且 `key_epoch ≥ min_key_epoch`
  - 包清单：接受任一 `epoch ≥ min_key_epoch` 的受信钥签名（包清单不携带 epoch）
  - `min_key_epoch` 只在渠道清单验签成功后取 `max(min_key_epoch, key_epoch)` 抬升；`epoch < min_key_epoch` 的钥处处被拒
- 校验顺序：
  - 渠道：拉取（https、≤ 4 MiB）→ 解析 → 验签（`key_epoch`）→ watermark → 抬升下限 → plan
  - 包：`size` + `sha256`（下载完成时）→ 写入层池 → 容器结构检查 → 清单签名（`min_key_epoch`）→ 清单解析（路径 / 策略 / parent 形状）→ blob 存在性 → 壳范围 → `id`/`version_code` 与渠道条目一致 → parent 链与其下同 id 层一致 → delta 物化

parent 链在 stage 时逐个校验：本批新包中带 `parent` 的，与修订中位于其下、`id` 相同的最近一层比对，`parent.version_code` 与 `parent.manifest_sha256` 必须同时相等；其下没有同 id 层的 patch 同样拒绝。任一不符 → `E_PARENT`，整次 stage 失败（不写黑名单）。只校验本批新包：继承下来的 committed 层在它们自己 stage 时已经查过，重查等于每次更新都要把整叠层的清单哈希重新推一遍。下层的清单哈希在 stage 时重新打开该包读出，不新增状态字段。渠道 `parent_version_code` 与 delta 的 `delta_base_sha256` 仍然是发布侧与解码侧的防线，三者互不替代。

### 3.4 Delta 与解码

- 算法：bsdiff 控制流 + zstd 压缩整个 patch 流；`encoding = zstd+bsdiff`
- 读取 blob：先比 `blob_size` 与实际长度，再比 `blob_sha256`，然后才解码
- 解码上限：`zstd` 输出以 `size` 封顶；`zstd+bsdiff` 的 patch 流以 `blob_size × 64 + 1 MiB` 封顶；超出 → `E_SPEC`
- 应用：解 zstd → bspatch(base_bytes)（输出按 `size` 精确预分配，`size` 不得超过单资源上限，§18）→ 校验结果 `sha256`
- 打包器策略（实现细节，不进格式）：
  - `size < --delta-threshold`（默认 262144）→ `full`
  - 压缩后 delta 体积不划算（≥ 新文件的 0.7）→ 退回 `full`
  - 包级上限：delta entry ≤ 64 **且** delta 结果总字节 ≤ 32 MiB，超出部分退回 `full`
  - `--parent` 可重复（base 在前，patch 依序在后），整条链在内存中解析（依次应用 full/delete/delta）后作为比较基准；第一个 `--parent` 不是 base → 拒绝；解码字节有单 entry 与整链上限（§10.3）
  - 解析后的 parent 链有而新 dist 无的路径 → 写 `delete` 墓碑

## 4. 渠道清单（CDN 静态文件即可）

URL 由原生配置指定，例如：

`https://cdn.example.com/tpk/{{channel}}/latest.json`

```json
{
  "spec": "tpk-channel/1",
  "channel": "stable",
  "published_at": "2026-09-08T15:00:00Z",
  "watermark": 202609081500,
  "key_epoch": 1,
  "min_shell": "2.3.0",
  "force_shell": null,
  "notes": "修复登录页样式",
  "packs": [
    {
      "id": "core",
      "kind": "base",
      "version": "1.0.0",
      "version_code": 20260901120000,
      "url": "https://cdn.example.com/tpk/stable/core-20260901120000.tpk",
      "size": 8400000,
      "sha256": "hex64"
    },
    {
      "id": "core",
      "kind": "patch",
      "version": "1.0.3",
      "version_code": 20260908150000,
      "parent_version_code": 20260901120000,
      "url": "https://cdn.example.com/tpk/stable/core-20260908150000.tpk",
      "size": 180000,
      "sha256": "hex64",
      "rollout": 10,
      "min_shell": "2.3.0"
    },
    {
      "id": "maps",
      "kind": "dlc",
      "version": "2.0.0",
      "version_code": 20260905090000,
      "url": "https://cdn.example.com/tpk/stable/maps-20260905090000.tpk",
      "size": 50000000,
      "sha256": "hex64",
      "optional": true
    }
  ]
}
```

分离签名：`latest.json.minisig`。

结构规则：

- `key_epoch`：签名覆盖；缺省 1，`0` 非法（§3.3）。
- `packs[].rollout`：`1..=100`，缺省 100，越界 `E_SPEC`。
- `patch` 必须带 `parent_version_code` 且小于自身 `version_code`；非 patch 禁止带。
- `(id, version_code)` 在同一清单中不得重复。
- `packs[].min_shell` / `packs[].max_shell`：严格 SemVer，可缺省；两者都给出时 `min_shell ≤ max_shell`，否则 `E_SPEC`；`tpk channel` 从各包签名清单原样抄写，供 plan 在下载前跳过壳范围外的包。
- `notes`：解析时先剥除标记、丢弃能隐藏或重排文本的格式字符（bidi 控制、零宽空格、tag 块等；ZWNJ/ZWJ 等整形字符保留），再折叠控制字符、trim，最后截断为 200 个可见字符，空则记为缺省；仅供日志与诊断，不是用户文案通道（完整清单见 §11.1 第 5 条）。
- `optional`：必须被解析。〔未实现〕客户端语义：plan 目前不区分 optional，DLC 与 base 一样被纳入计划。
- App Store 构建（§11.1 第 1 条）下 `kind` 恰为 `dlc` 或 `mod` 的条目在反序列化时**被丢弃**，而不是让整份清单失败——一个 DLC 条目不得挡住这批客户端的 base 与安全更新。其余未知 `kind` 仍使整份清单失败（`E_SPEC`）。

客户端规则：

- **watermark**：按渠道持久化已见最大值。拒绝**严格更小**的清单（`E_WATERMARK`，防重放），接受相等——同一分钟重复发布不应让已见前一份的设备永久失效。按渠道记录——切到别的渠道再切回不应永久丢弃原渠道的清单。
- 验签通过的清单无论是否有可用包，都先推进该渠道 watermark 与 `min_key_epoch` 并落盘，再做 plan。
- **验签失败**：返回错误，由调用方稍后重试，不写 blacklist——blacklist 是包级机制，CDN 瞬时不一致不能永久禁掉好包。
- **壳版本**：`force_shell` 或渠道 `min_shell` 高于当前壳 → `shell_required`，不应用任何 pack。`force_shell` 连热修复一起停，只在确实不希望这批壳收到任何内容时使用。包自身的 `min_shell`/`max_shell`：渠道条目带有时 plan 先行跳过；stage 时以签名清单再查一次（§7）。
- **选包（plan）**：候选按 `(kind 序 base<patch<dlc<mod, version_code)` 升序逐个判定，维护每个 `id` 的投影版本（初值为已安装版本）：
  - `kind = mod` → 跳过（mod 永不经渠道下发）
  - 命中 blacklist（§5）→ 跳过
  - 当前壳低于渠道条目 `min_shell` → 跳过（`ShellTooOld`）；高于 `max_shell` → 跳过（`ShellTooNew`）；边界含等号
  - 被取代 → 跳过（`Superseded`）：预扫一遍，对每个 `id` 取通过全部单包规则（mod、blacklist、壳范围、非 patch 的版本规则即 `version_code` 高于已安装版本且不低于 `version_floor`、rollout）的最高 base/DLC `version_code`；低于它的同 id base/DLC，以及 `parent_version_code` 低于它的 patch，均被取代。新设备落在 base 灰度桶内时只下新 base
  - `patch`：只有 `parent_version_code == 投影版本` 时入选
  - 其他 kind：两条规则同时成立才入选——`version_code > 投影版本`（相等也拒绝：已经装着就不必再下一遍），否则跳过（`NotNewer`）；且 `version_code ≥ version_floor[id]`（§5），否则跳过（`Downgrade`）。两个原因分开报：`NotNewer` 是寻常的「已经是最新」，`Downgrade` 是防回滚下限真的挡下了一个包，值得被看见。两者问的不是同一个问题：投影版本来自真实在装的层，回答「patch 能叠在什么上面」；`version_floor` 是该 `id` 曾经 commit 过的最高版本，回答「这个 `id` 最多能退到哪」。对 floor 只拒**严格更小**，相等放行——floor 比层活得久（`reset` 保留），若连相等也拒，刚 `reset` 的设备连自己本来在跑的那一版都拉不回来，只能一直停在 embedded；相等是重装，更旧才是降级
  - 不在 rollout 桶内 → 跳过
  - 入选后投影版本 = 该包 `version_code`
  - 某 `id` 的已装层被 condemn 时，该 `id` 的投影初值随之下降（可降到 0）：其上的 patch 因 `parent_version_code` 不再等于投影值而落选，plan 转而选中该 `id` 可用的最高 base。`version_floor` 不随之下降，所以同 `id` 更旧的签名包仍进不来
- 已安装版本 = committed 与 booting 修订中每个 `id` 的最大 `version_code`，**不计已命中 blacklist 的层**。被 condemn 的层不算装着：活动修订（§7 步骤 3）、stage 的继承过滤（§6.2）与 staged 晋升检查（§7 步骤 2）都已把它丢掉，plan 若仍当它在，就会一直挑它上面的 patch，而这些 patch 每次都在 stage 被 `E_PARENT` 拒绝——同一份必然失败的下载每次 check 都重来一遍。把它从已安装版本里去掉，plan 才会改要一份完整 base。这个值只用来回答「patch 能叠在什么上面」与「是不是已经装着了」；「能不能退版本」由 `version_floor`（§5）回答，否则 condemn 一个层就等于把该 `id` 的降级下限清零，旧包可以原样装回来。
- 缺失 parent 的 patch 不可单独应用。plan 只在渠道列出的包中按上述规则选择，不会自行改下 base 或拼接渠道外的包；设备能否追上取决于渠道是否列出所需的 base 与中间 patch。
- **rollout 分桶**：`sha256(install_id ‖ ":" ‖ id ‖ ":" ‖ version_code)` 前 8 字节按 big-endian u64 取 `% 100 < rollout`。不在桶内照常推进 watermark。

## 5. 磁盘布局（冻结）

两个根，均在插件 `setup` 中经 `app.path()` 解析：

```
$APPLOCALDATA/tpk/              持久根
  state.json                    三态指针、修订、计数器、watermark、key epoch 下限
  blacklist.json                结构化黑名单
  layers/
    <file_sha256>.tpk           内容寻址层池；文件名即整包 sha256

$APPCACHE/tpk/                  缓存根，系统可随时清空
  materialized/
    <result_sha256>             delta 物化结果；文件名即结果内容 sha256
  tmp/
    <pack_sha256>.part          下载中的包
    <pack_sha256>.tpk           size + sha256 校验通过后由 .part rename 而来；不跨根 rename 进 layers/，
                                stage 以原子写另存层池副本；本次 download 结束（成功或失败）即删除；
                                崩溃遗留的由下一次 download 开始时清理
```

规则：

- 层池只增不移：同一文件被多个修订引用只存一份。晋升、回滚、reset 都只改 `state.json`，不移动层文件。
- 缓存根下任何文件都不能被假定仍然存在；持久根下任何文件都不能被假定可以从缓存根重建。
- 原子写：写唯一临时文件 `<name>.tmp.<pid>.<n>` → `fsync` → `rename` → `fsync` 父目录。临时名每次调用唯一，并发写同一目标互不冲突；内容寻址文件 rename 失败但目标已存在时视为成功。
- `gc()` 引用计数：删除 `layers/` 中未被 staged/booting/committed 任一修订引用的文件，以及 `materialized/` 中这些修订的 delta entry 不再需要的结果；超过 1 小时的临时文件一并删除，更新的临时文件视为写入进行中而保留。幂等、可中断。在 `notify_ready()` 成功提交 booting 修订后与 `reset()` 后执行；回滚或被丢弃的 staged 修订遗留的层在下一次成功提交时释放。提交后的 gc 失败只记日志。
- `state.json` 不可解析、`spec` 未知或 `rev` 形状非法，视为全新状态；`blacklist.json` 不可解析视为空黑名单。启动继续，落到 embedded。
- `layers/` 应排除出平台备份；`state.json` 与 `blacklist.json` 留在备份内。见 §11.1。

`state.json`：

```json
{
  "spec": "tpk-state/1",
  "pointer": "booting",
  "install_id": "8f14e45f-ceea-467a-9a2f-0b8f5c8b3a21",
  "booting": {
    "rev": "rev-8",
    "layers": [
      {
        "id": "core",
        "kind": "base",
        "version_code": 20260901120000,
        "file_sha256": "hex64",
        "size": 8400000,
        "mtime_ns": 1788268800000000000
      },
      {
        "id": "core",
        "kind": "patch",
        "version_code": 20260908150000,
        "file_sha256": "hex64",
        "size": 180000,
        "mtime_ns": 1788879600000000000
      }
    ]
  },
  "committed": {
    "rev": "rev-7",
    "layers": [ "…" ]
  },
  "boot_attempts": 1,
  "consecutive_rollbacks": 0,
  "last_watermark": { "stable": 202609081500, "beta": 202609101200 },
  "version_floor": { "core": 20260908150000 },
  "min_key_epoch": 1
}
```

字段规则（schema：`spec/json-schema/store-state.schema.json`）：

- `spec` 必须为 `tpk-state/1`。
- `pointer`：`committed | booting`，决定本次启动加载哪个修订。
- `staged` / `booting` / `committed`：可缺省（缺省即无）。`rev` 形如 `rev-<n>`；新修订取三者中最大 `n` 加一。`layers` 按叠加顺序由低到高。
- `LayerRecord`：`id`、`kind`、`version_code`、`file_sha256`（亦为层池文件名）、`size`、`mtime_ns`（stage 时记录）。
- `install_id`：UUIDv4 形状，首次创建时生成；`reset` 保留——重新生成会把设备移入另一个灰度桶。
- `boot_attempts`：当前 booting 修订的启动次数（§7）。
- `consecutive_rollbacks`：连续回滚次数。
- `last_watermark`：按渠道记录的已见最大 watermark；`reset` 保留。
- `version_floor`：`{pack_id: version_code}`，该 `id` 在本设备上曾经 commit 过的最高 `version_code`。只在 commit（含 seed 直接成为 committed）时抬升——stage 不抬：staged 可能被丢弃、booting 可能被回滚，没真正跑起来的版本不该抬高门槛——永不下降，`reset` 保留。与「已安装版本」（§4）不是一回事：condemn 一个层会把它从栈里拿走，plan 必须不再当它装着，但同 `id` 更旧的签名包仍须拒绝，这就是本字段的全部职责。缺省 `{}`，旧 `state.json` 照常加载：`Store::open` 会回填一次，来源是 committed 修订的层与 `blacklist.json` 中 `reason ≠ not_acknowledged` 的条目（`version_code = 0` 的占位条目跳过）。`staged`、`booting` 与 `not_acknowledged` 有意不作为来源——三者说的都是「上过试用台但从未被确认」的修订，没跑起来的版本不该挡住跑起来的那个。黑名单这一路是关键：被 condemn 的层会被 `write_revision` 从栈里丢掉，下一次 commit 后它的 `version_code` 就永远离开了 `committed.layers`，不回填的话该 `id` 的下限会一直停在 0，旧包正是从这个洞走回来的。只有真的抬升了才写 `state.json`，正常启动一次不写盘。
- `min_key_epoch`：单调 key epoch 下限，缺省 1；`reset` 保留。
- `last_error`：`{code, message}`，可缺省。只记最后一次「挡住修订进入 staged」的失败：渠道轮询失败、下载失败（含读回下载结果的 `E_IO`）、stage 被拒。不记业务结果（up_to_date、`shell_required`、黑名单、`disabled`），否则只是落后一个壳版本的设备会永久显示错误。渠道清单拉取并验签成功、stage 成功、`notify_ready()` 提交，三者都会清空它。重复记录完全相同的 `{code, message}` 不重写 `state.json`——离线设备循环轮询会以同样方式失败，不该为没有变化的内容每次 fsync。不带时间戳。

`blacklist.json`：

```json
{
  "entries": [
    {
      "sha256": "hex64",
      "id": "core",
      "version_code": 20260908150000,
      "reason": "not_acknowledged",
      "count": 3,
      "first_seen": 1788879600
    }
  ]
}
```

- `reason`：`signature | spec | path | parent`（永久）；`io | hash | delta | not_acknowledged`（瞬态）。错误码映射：`E_SIGNATURE/E_PATH/E_PARENT/E_HASH/E_DELTA/E_IO` 各对应同名 reason，其余码（含 `E_STATE`）记为 `spec`（永久）。`E_SHELL` 从不记入黑名单：壳不匹配不是包的问题。
- 匹配：`sha256` 相等，**或** `(id, version_code)` 相等——重新打包同一版本换了 sha256 也绕不过去。
- 永久条目立即生效、永不过期。瞬态条目 `count ≥ 3` 才生效，`first_seen`（Unix 秒）起 30 天后过期并被清理。
- 同一条目再次记录：`count + 1`；永久 reason 覆盖瞬态，反之不覆盖。
- `condemn`：直接记满三振、立即生效，30 天 TTL 仍适用（用于回滚，§7）。
- 上限 256 条，超出丢最旧。
- plan（§4）、stage 与 boot（§7）三处都查。

Seed：若配置了 `plugins.tpk.seed_dir`（相对 resource 目录），且当前无 committed 修订，则目录内全部 `.tpk` 以当前 `min_key_epoch` 验签后写入层池，直接成为 committed 修订（不经 booting 试用）。失败只告警。

## 6. 叠加与解析（冻结语义）

### 6.1 层序

Embedded（编译进壳，永不可删）之上，活动修订的层按 `(kind 序, version_code)` 升序叠加：

1. `base`
2. `patch`
3. `dlc`
4. `mod` 〔未实现：mod 层在建索引时一律拒绝加载〕

排序是全局的，不按 `id` 分组。

### 6.2 修订的组成（stage 时决定）

stage 一组新包时，新修订 = 从**活动修订**（pointer 为 booting 时取 booting，否则取 committed）继承的层 + 新包：

- 新包为非 patch（base/dlc/mod）：替换活动修订中同 `id` 的全部层（含其 patch）。
- 新包为 patch：叠在同 `id` 已有层之上。
- 其他 `id` 的层原样继承。
- 被黑名单拦截的层不继承。
- 按 `file_sha256` 去重，再按 §6.1 排序。

从活动修订而非 committed 继承：试用期间下载的更新不得悄悄丢掉正在试用的层（plan 已把它们算作已安装）。若该试用随后被回滚，它的层被 condemn，含这些层的 staged 修订在下次 boot 时被丢弃（§7）。

### 6.3 索引

setup 时对活动修订每层：读整文件核对 `file_sha256` → 以 `min_key_epoch` 验清单签名 → 解析清单 → `kind = mod` 拒绝。任一步失败，该层跳过并记入 `status().failed_layers`，同时按失败码映射的 reason（§5）给该层记一次 strike（`E_IO`、`E_HASH` 为瞬态）；不崩溃。以下不记 strike：`E_SHELL`（换个壳即可运行）、`E_SIGNATURE`（层池中的层在 stage 时已验过签，且哈希核对在验签之前、篡改会表现为 `E_HASH`，故此时验签失败意味着信任集或 key 下限变化，而非坏包）、mod 层被拒、层栈已满。

〔未实现〕启动时只按 stage 时记录的层文件元数据（`size`、`mtime_ns`）比对，替代整文件哈希。

索引为 `HashMap<Box<str>, Loc>`，每个 path 只保留**最高层**的 entry。高层 `delete` 遮蔽低层与 embedded；高层 `full`/`delta` 覆盖低层 `delete`。`get` 热路径禁止重新解 ZIP 中央目录。索引构建完成后装入 `OnceLock`，进程生命周期内不再替换。

### 6.4 `get(path)`

```
loc = index.lookup(path)
if loc is None:            return NotFound         → 由 embedded 回答
if loc.op == delete:       return Deleted          → 不得回退 embedded
if cache.hit(path):        return cached
match loc.op:
  full  → 从该层容器读 blob：校验 blob_size、blob_sha256 → 解码（上限见 §3.4）
  delta → 从 materialized/<sha256> 读结果
          缺失 → NotMaterialized                  → 本次回退 embedded，见 §6.5
校验 sha256(bytes) == entry.sha256
  full 不符  → LayerCorrupt                        → 本次回退 embedded
  delta 不符 → NotMaterialized（结果文件已被删除）
cache.insert(path, bytes); return bytes
```

- 运行时读取失败只记日志并回退 embedded，不写黑名单；若因此白屏，由 §7 三态回滚兜底。只缓存成功结果，物化结果补齐后同一 resolver 即可服务。
- 后置 sha256 校验必须保留：它是唯一覆盖「blob 或物化结果落盘后被改写」的检查。
- 资源键回退链与 Tauri 一致：`key` → `key.html` → `key/index.html`，逐个先查 overlay；命中墓碑即返回无内容。
- `iter()`：overlay 可见路径（不含墓碑）与 embedded 的并集，overlay 优先。

### 6.5 Delta 物化

- delta 在 `stage()` 中物化：对合并后栈中的每一层，以栈中**位于它之下的层**构建解析器，取 base → 核对 `delta_base_sha256` → bspatch（§3.4）→ 核对结果 `sha256` → 原子写入 `$APPCACHE/tpk/materialized/<result sha256>`。结果已存在则跳过。新包任一 entry 失败 → stage 失败（`E_DELTA`），不产生修订；继承层缺失的结果尽力修复，失败只记日志。
- `boot()` 从不物化。
- `materialized/` 位于缓存根，可被系统清空。setup 发现活动修订所需的物化结果缺失时，起后台线程重新物化，setup 不等待；完成前对应 path 回退 embedded，缺失从不计入任何 strike。读到哈希不符的结果文件会被删除，随后重建。
- 〔未实现〕缺失 entry 标 `Pending`，`get` 只阻塞该 entry 等待物化完成；`max_boot_blocking_ms` 预算（§18）。
- 〔未实现〕`max_delta_chain_depth`（§18）。

### 6.6 缓存

内存 LRU，按字节计预算，键为 path：桌面 32 MiB、移动 8 MiB，`cache_budget_bytes` 可配，`0` 关闭。单个对象超过预算 1/4 不入缓存。

### 6.7 读取实现

每层常驻已验签的容器读取器，同层读取互斥、跨层并行。〔未实现〕建索引后抄出每个 blob 的 `(data_start, compressed_size, method)`、丢弃 `ZipArchive`、以 `read_at`/`seek_read` 无锁读取。

### 6.8 CSP

- `tpk pack` 拒绝含非空内联 `<script>` 的 HTML（JSON 数据块除外，§10.3）。
- overlay 为所有可见 `.js`/`.mjs` 计算内容 hash（先 CRLF/CR → LF），在首次 `csp_hashes` 调用时算一次并常驻。已知缺口：此时尚未物化的 delta 脚本不计入。
- `csp_hashes(html_path)`：overlay 服务或墓碑遮蔽了该 HTML → 只返回 overlay 脚本 hash；否则返回 embedded 的 hash 再加 overlay 脚本 hash。

### 6.9 非目标

TPK 不是媒体分发通道。`tauri://` 不支持 Range 请求，包内音视频无法 seek；`asset://` / `convertFileSrc` 不经 Assets，看不到叠加层。

## 7. 三态状态机（冻结）

```
committed ──download → stage()──────────────────────► staged
staged ──冷启动 boot()，无试用中修订、未被拉黑─────► booting        boot_attempts = 1
staged ──冷启动 boot()，任一层被拉黑────────────────► 丢弃
booting ──notify_ready()────────────────────────────► committed      boot_attempts = 0，consecutive_rollbacks = 0
booting ──冷启动 boot()，boot_attempts + 1 < 3──────► booting        重试，不拉黑
booting ──冷启动 boot()，boot_attempts + 1 ≥ 3──────► 回滚到 committed（无 committed → Embedded）
```

`boot()`（插件 setup 中、任何窗口创建前执行一次）：

1. 若 `pointer = booting` 且有 booting 修订：`boot_attempts + 1`。达到 3：对该修订中**不属于 committed 修订**的层 `condemn(not_acknowledged)`，丢弃 booting，`pointer = committed`，`boot_attempts = 0`，`consecutive_rollbacks + 1`。继承自 committed 的层已被确认过，不连坐。
2. 然后若 `pointer = committed` 且有 staged 修订：任一层被黑名单拦截 → 丢弃 staged；否则 staged 成为 booting，`pointer = booting`，`boot_attempts = 1`。步骤 1 回滚后同一次 boot 内即可晋升新的 staged。
3. 活动修订 = `pointer` 指向的修订，去掉被黑名单拦截的层。
4. 一次原子写 `state.json` 与 `blacklist.json`。

即：一个修订获得两次试用启动，第 3 次冷启动仍未确认则回滚。杀进程、掉电、用户退出与坏包在此层面无法区分，移动端尤其常见，一次失败即拉黑会误杀正常发布。

`boot()` 不物化 delta，不做与资源总字节数成正比的工作〔未实现：当前 setup 建索引时对每层整文件哈希，§6.3〕。物化不进 boot，避免慢设备被启动看门狗杀掉后被误判为坏包。

`notify_ready()`：有 booting 修订则成为 committed，`pointer = committed`，`boot_attempts = 0`，`consecutive_rollbacks = 0`，清 `last_error`；在返回给 JS 之前完成 `state.json` 的 fsync + rename，不另起异步任务；随后同步执行 `gc()`（§5）。否则 `noop`。可重复调用。

`stage()`：

1. 任一新包被黑名单拦截 → `E_BLACKLIST`。
2. 每个新包原子写入层池（已存在则不重写）；从层池文件重新打开验签（`min_key_epoch`）。
3. 当前壳不在包签名清单的 `[min_shell, max_shell]` 内 → 失败（`E_SHELL`，不写黑名单：换个壳即可 stage）；清单 `id`/`version_code` 与渠道条目不一致 → 失败（`E_HASH`）。
4. 按 §6.2 组成修订，按 §6.5 物化 delta。
5. 新修订写入 `staged`（覆盖之前未启动的 staged），原子写 `state.json`。写 `state.json` 即提交点；此前崩溃只留下孤儿文件。

`reset(clear_blacklist = false)`：状态重建为空（无 staged/booting/committed，计数清零），保留 `install_id`、`last_watermark`、`min_key_epoch`；`clear_blacklist = true` 时清空黑名单；随后 `gc()`。下次启动：Embedded + seed（若配置）。需 `tpk:allow-reset`。

降级：`consecutive_rollbacks ≥ 3` 时 `status().degraded = true`，`check()` 直接返回 `degraded` 且不访问网络；配置值不被改写。`reset`，或一次成功提交 booting 修订的 `notify_ready`，解除降级。

规则：

- 进程内不切层。WebView 始终看 setup 时装入 `OnceLock` 的索引；新内容与内容回滚都在下一次冷启动生效。唯一例外：§6.5 后台补物化完成后，原先回退 embedded 的 delta path 开始返回物化结果。
- 不存在「渲染 N 秒就算成功」。
- setup 永不使 `Builder::build` 失败：缺配置、磁盘、公钥、壳版本等问题记录日志，插件对本次启动保持 inert，由 embedded 服务。例外在 setup 之前：`plugins.tpk` 存在但反序列化失败时，Tauri 在 setup 前解析它，`Builder::build`/`run` 返回 `Err`，应用不启动（§8.1）。
- 回滚不发 `tpk://state`：setup 早于任何窗口，事件无人接收。本次启动回滚的修订经 `status().rolled_back` 报告。

## 8. 原生配置

`tauri.conf.json` 的 `plugins.tpk`。最小配置：

```json
{
  "plugins": {
    "tpk": {
      "manifest_url": "https://cdn.example.com/tpk/{{channel}}/latest.json",
      "pubkeys": [{ "key": "RWT...", "epoch": 1 }]
    }
  }
}
```

### 8.1 字段

| 字段 | 类型 | 默认（桌面 / 移动） | 含义 |
|---|---|---|---|
| `manifest_url` | string | **必填** | 渠道清单 URL 模板，展开后必须是 `https://` |
| `pubkeys` | `[{key, epoch}]` | **必填** | 受信签名公钥（minisign base64）；`epoch` 缺省 `1`，`0` 非法 |
| `enabled` | bool | `true` / `true` | `false` 时插件不工作，只服务 embedded |
| `channel` | string | `"stable"` / `"stable"` | 轮询的渠道 |
| `auto_check_on_launch` | bool | `true` / `false` | 启动时自动 `check`：setup 末尾起一个任务执行，不阻塞启动 |
| `auto_download` | bool | `true` / `false` | 仅限定启动检查：该次 `check` 发现更新后自动 `download`；对前端发起的 `check` 无效 |
| `cache_budget_bytes` | u64 | 32 MiB / 8 MiB | 解码后资源的内存 LRU 预算；`0` 关闭缓存 |
| `headers` | `{string: string}` | `{}` | 附加到清单与 pack 请求的 HTTP 头。路由元数据，不是安全边界 |
| `seed_dir` | string | 未设置 | 应用包内 seed pack 目录，相对 resource 目录（§5） |

- 仅以上 9 个键。该节使用 `deny_unknown_fields`：`plugins.tpk` 存在时，未知键（含拼写错误）、缺必填字段、类型错误都会使反序列化失败，`Builder::build`/`run` 返回 `Err`，应用启动失败；使用 `init_with_config` 时同样适用。节名拼错（如 `plugins.tkp`）或缺失该节等同于无配置：记录日志，插件保持 inert。
- 启动自动更新复用 `check` / `download` 命令的代码路径，事件与前端自行调用时完全一致；失败只落日志与 `last_error`（§5），不阻止启动、不计 strike。degraded 设备在 `check` 内即返回 `degraded`，不发起任何网络请求；`enabled = false` 或 setup 放弃 OTA 时插件状态未注册，该任务什么都不做。
- 移动端缓存预算更小：同一份字节跨 WebView bridge 还会再拷贝一次。

### 8.2 `manifest_url` 模板

只允许 4 个变量，其余一律报错（`E_SPEC`）：

| 变量 | 取值 |
|---|---|
| `{{channel}}` | `channel` 配置值 |
| `{{arch}}` | 编译目标 CPU 架构，如 `aarch64` |
| `{{target}}` | `{arch}-{os}`，如 `aarch64-macos` |
| `{{shell}}` | 壳版本（`package.version`，SemVer） |

- 变量名两侧允许空白：`{{ channel }}`；未闭合的 `{{` 报错。
- 展开在每次 `check` 时进行；非 https 结果拒绝（`E_SPEC`，不落 blacklist）。
- 模板封闭是刻意的：开放模板等于允许把更新源指向别处。

### 8.3 `pubkeys` 与 key epoch

```json
"pubkeys": [
  { "key": "RWTnew...", "epoch": 2 },
  { "key": "RWTold...", "epoch": 1 }
]
```

验签语义见 §3.3。轮换：新钥以更高 epoch 加入壳，新旧共存一个发布周期；渠道清单以新 `key_epoch` 签名后，客户端下限抬升，旧钥即被轮出。撤销时效见 §12。

### 8.4 不可由 JS 修改

`manifest_url`、`pubkeys`、`channel`、`headers` 没有任何运行时 setter，也没有命令能改写。前端 XSS 不能把更新源指走。

### 8.5 代码内配置

```rust
use tauri_plugin_tpk::{PubKey, TpkConfig};

let config = TpkConfig::new(
    "https://cdn.example.com/tpk/{{channel}}/latest.json",
    vec![PubKey { key: "RWT...".into(), epoch: 1 }],
)
.channel("beta");

tauri::Builder::default()
    .plugin(tauri_plugin_tpk::init_with_config(tpk, config))
```

- 代码内配置优先；此时 `plugins.tpk` 可省略，但若存在仍须能反序列化（§8.1）。
- 只用于构建期决定的值（feature flag 选渠道）；禁止从可变来源读 URL / 公钥。

### 8.6 不是配置键

以下名字在本文其他章节出现，但不是 `plugins.tpk` 的键，写入会因 `deny_unknown_fields` 导致启动失败：

| 名字 | 说明 |
|---|---|
| `min_shell` | 发布侧由 `tpk pack --min-shell` 写入签名清单（§10.3、§17.4） |
| `allow_mods` / `mod_protected_globs` | 〔未实现〕Mod 层（§9.1 `set_mod_enabled`、§12） |
| `max_boot_blocking_ms` | 〔未实现〕平台默认值见 §18 |
| `max_delta_chain_depth` | 〔未实现〕平台默认值见 §18 |

新内容的生效时机固定为下一次冷启动（§7），无配置项。

## 9. 插件命令与事件（冻结）

权限（Tauri ACL，`tpk:` 命名空间；`permissions/autogenerated/` 由 `build.rs` 生成）：

| 权限 | 授予 |
|---|---|
| `tpk:default` | `check` `download` `notify_ready` `status` |
| `tpk:allow-reset` | `reset` |
| `tpk:allow-mods` | `set_mod_enabled` |
| `tpk:deny-all` | 拒绝全部 6 个命令 |

默认只给主窗口 `tpk:default`。`reset` 不在默认集：`clear_blacklist` 会让已判坏的发布重新可装，属客服能力。

pack 内容运行在 `tauri://localhost`，继承窗口的全部 capability。`status().unsafe_capabilities` 列出主窗口已授予、可让 overlay JS 触达原生能力的权限（`shell:allow-execute` `shell:allow-spawn` `shell:allow-open` `shell:default` `process:allow-restart` `fs:allow-write-file` `fs:allow-write-text-file` `fs:default`）。只提示，不阻断；期望值为空。

### 9.1 Commands

命令名 `plugin:tpk|<name>`。业务分流走返回值的 `status` 字段；`Err` 序列化为 `{ code: ErrorCode, message }`，`code` 为 14 个冻结码之一。

`check() → CheckOutcome`

```ts
type CheckOutcome =
  | { status: "up_to_date"; watermark: number }
  | { status: "available"; packs: PackSummary[]; bytes: number; notes?: string }
  | { status: "shell_required"; min_shell: string }
  | { status: "disabled" }
  | { status: "degraded"; consecutive_rollbacks: number }

interface PackSummary {
  id: string;
  kind: "base" | "patch" | "dlc" | "mod";
  version: string;
  version_code: number;
  size: number;
}
```

- `degraded`：§7 降级态，不联网直接返回。
- 验签通过的清单先推进 watermark 与 `min_key_epoch` 并落盘，再 plan（§4）。
- blacklist 命中、壳范围外、被取代与 rollout 桶外的 pack 在 plan 中被跳过，不单独成为 outcome；全部跳过即 `up_to_date`。
- `shell_required` **不携带 url**；插件不提供任何升壳 UI。
- `notes`：已按 §11.1 第 5 条剥除标记、丢弃可隐藏或重排文本的格式字符并截断到 200 个可见字符，**仅供日志**；前端若展示必须按纯文本渲染。
- 清单拉取失败、验签失败、watermark 回退以 `Err` 返回（同时发 `tpk://error`）。
- 结果（清单 + plan）缓存在进程内，供随后的 `download` 使用。

`download() → DownloadOutcome`

```ts
type DownloadOutcome =
  | { status: "staged"; rev: string; bytes: number }
  | { status: "up_to_date" }
  | { status: "shell_required"; min_shell: string }
  | { status: "disabled" }
  | { status: "failed"; code: ErrorCode; message: string }
```

- 没有缓存的 plan 时内部先执行一次 `check`；该 `check` 的 `Err` 原样返回。降级态下此路径得不到 plan，返回 `Err`（`E_STATE`）。
- 下载断点续传：`.part` 位于 `$APPCACHE/tpk/tmp/`，续传用 Range；有待下载的 plan 时，开始下载前清理 `tmp/` 中不属于本次 plan 的 `.part` 与 `<sha256>.tpk`（含崩溃遗留）。
- 下载完成的包定稿为 `$APPCACHE/tpk/tmp/<sha256>.tpk`，不跨根 rename 进层池（两根可能不在同一文件系统）；stage 以原子写（fsync）写入层池；这些文件在本次调用结束时删除，无论成功失败。读回失败返回 `failed`（`E_IO`）。
- 传输错误与 `stage` 失败（验签、哈希、壳范围、delta、黑名单、磁盘）返回 `failed`；`message` 中 URL query 已脱敏。
- `staged`：已下载、校验、物化 delta，**下次冷启动生效**。修订组成见 §6.2。

`notify_ready() → ReadyOutcome`

```ts
type ReadyOutcome = { status: "committed"; rev: string } | { status: "noop" }
```

- 语义见 §7；返回前完成落盘。

`status() → Status`

```ts
interface Status {
  pointer: "committed" | "booting";
  rev?: string;                   // 当前加载的 rev；无则为 embedded
  layers: { id: string; kind: "base" | "patch" | "dlc" | "mod"; version_code: number }[];  // 低层在前
  shell: string;
  watermark: number;              // 当前 channel 的 watermark 下限
  pending: boolean;               // 有 staged rev 等待下次冷启动
  degraded: boolean;
  failed_layers: string[];        // 本次启动加载失败的层 file_sha256
  rolled_back?: string;           // 本次启动 setup 中被回滚的 rev，进程内不变（reset 不清除）；无则省略
  unsafe_capabilities: string[];
  has_embedded_fallback: boolean; // false = 二进制无 index.html，回滚无处落地，视为构建错误
  last_error?: { code: ErrorCode; message: string };
}
```

- `last_error`：最后一次挡住修订进入 staged 的失败，与 `tpk://error` 同源（同一 `code`/`message`）。写入与清空规则见 §5：一次成功的 `check`（清单已拉取并验签）、一次成功的 stage、一次 `notify_ready()` 提交都会清空它；重复的同一失败不重写状态。业务结果不写入，因此 `status().last_error` 缺省不等于「上次检查成功」。

`reset(options?: { clear_blacklist?: boolean }) → Status`

- 需 `tpk:allow-reset`。语义见 §7；返回重置后的 `Status`，发 `tpk://state`（`reset`）。

`set_mod_enabled(id: string, enabled: boolean) → void`

- 需 `tpk:allow-mods`。命令名与权限名已冻结，插件启用时恒返回 `Err`（`E_SPEC`）。
- 〔未实现〕Mod 层：`trusted = false`、受保护 glob、仅桌面（§11.1、§12）。

`Err` 的使用边界：编程错误、未初始化（`E_STATE`）、无法分类的 IO，以及 `check` 的网络 / 验签 / watermark 失败。其余业务结果走 outcome。`enabled = false` 或 setup 放弃 OTA 时插件状态未注册，命令仍按冻结形状应答：`check`/`download` 返回 `{ status: "disabled" }`，`notify_ready` 返回 `{ status: "noop" }`，`status`/`reset`/`set_mod_enabled` 返回 `Err`（`E_DISABLED`）。

### 9.2 Events

| 事件 | payload | 触发 |
|---|---|---|
| `tpk://download-progress` | `{ downloaded, total, pack_index, pack_count }` | 下载每个 pack 时；`downloaded/total` 为当前 pack 的字节 |
| `tpk://state` | `{ pointer: "staged" \| "committed" \| "reset", rev? }` | `download` 成功 / `notify_ready` 提交 / `reset` |
| `tpk://error` | `{ code: ErrorCode, message }` | 清单拉取、验签、下载、stage 失败 |

- `rev` 缺失时省略字段。
- setup 中的回滚不发事件（早于任何窗口存在），以 `status().rolled_back` 为准（§7）。

### 9.3 前端约定

guest 包 `tauri-plugin-tpk-api`：`check` `download` `notifyReady` `status` `reset({ clearBlacklist })` `onDownloadProgress` `onState` `onError`。

```ts
await router.isReady();
await firstDataLoad();
await notifyReady();          // 首屏真正渲染之后，不是入口顶部

const c = await check();
if (c.status === "available") {
  const d = await download();
  if (d.status === "staged") {
    // 提示「下次启动生效」；不要 reload WebView，不要热替换正在跑的模块图
  }
}
```

- `notifyReady` 是内容自证可用；放在入口顶部等于关闭回滚保护。
- `check` / `download` 按 `status` 分支，不靠 `try/catch` 做业务判断；`catch` 只处理 `code`。

## 10. CLI（构建与发布）

二进制名 `tpk`（crate `tpk-cli`）。六个子命令；delta 由 `pack --parent` 内部生成，没有独立的 diff 子命令。

```
tpk keygen  [--out signing.key] [--comment "tpk signing key"]
tpk pack    --kind base|patch|dlc|mod --id core --version 1.0.3
            --version-code 20260911150000 --created-at 2026-09-11T15:00:00Z
            [--min-shell 2.3.0] [--max-shell X] [--channel stable]
            --dist ./dist [--parent ./core-20260901120000.tpk ...]
            [--delta-threshold 262144] --out ./core-20260911150000.tpk
tpk sign    --file F [--file F ...] [--trusted-comment tpk]
tpk channel --channel stable --pack P [--pack P ...] --url-base https://cdn/.../
            [--watermark auto|N] [--key-epoch 1] [--published-at RFC3339]
            [--rollout 1..100] [--min-shell X] [--force-shell X] [--notes S]
            --out latest.json
tpk inspect FILE.tpk [--json]
tpk verify  --pubkey B64 [--pubkey ...] [--epoch N ...] [--min-epoch 1]
            --file F [--file F ...]
```

### 10.1 退出码

| 码 | 含义 |
|---|---|
| 0 | 成功；`--help` / `--version` |
| 2 | 校验失败：签名/摘要/清单不合法、HTML/扩展名规则违反、`--parent` 搭配非 patch kind、parent id 与 `--id` 不一致、parent 包无法读取或 parent 链接不合法（第一个不是 base、后一个不是前一个的 patch、delta base 或重建结果不符）、parent entry 声明 `size` 或 `blob_size` 超过 64 MiB、parent 链累计解码超过 1 GiB、bsdiff 失败 |
| 3 | 参数或输入不可用：命令行参数解析失败、`TPK_SIGNING_KEY` 缺失/不可解析、SemVer 不合法、`--rollout` 越界、`--url-base` 非 https、目录不存在/空/含 symlink、keygen 目标已存在 |

CI 必须以 `verify` 作为上传前闸门（使用**公钥**）。

### 10.2 密钥与环境变量

- 唯一读取的环境变量：`TPK_SIGNING_KEY`（`pack` / `sign` / `channel` 使用）。接受完整两行 `.key` 文件或单行 base64 body。
- 私钥为未加密 minisign 格式；不支持口令加密的私钥。
- 禁止把私钥放进仓库。CLI 不把私钥写盘；`keygen --out` 以 `0600`（unix）新建写入，目标已存在即拒绝；不带 `--out` 时私钥打到 stdout。
- `keygen` 同时输出 `{ "key": "<base64>", "epoch": 1 }` 供粘贴进 `plugins.tpk.pubkeys`。

### 10.3 `tpk pack`

输入与校验：

| 规则 | 行为 |
|---|---|
| `--id` | `[a-z0-9][a-z0-9-]{0,62}` |
| `--version` / `--min-shell` / `--max-shell` | SemVer；`--max-shell` 打印告警（新壳发布后该包失效） |
| `--version-code` | 推荐 UTC `YYYYMMDDHHMMSS` |
| `--created-at` | **必填**，不默认 `now()`（确定性输出的前提） |
| `--dist` | 必须是非空目录；遇 symlink 拒绝；路径须 UTF-8 |
| 扩展名 | 每个文件名必须含 `.` 且不以 `.` 结尾，否则拒绝（Tauri 按请求路径推断 mime，未知扩展名会被当作 `text/html`） |
| HTML（`.html`/`.htm`） | 拒绝：① 非空内联 `<script>` 体（`</script` 后须为 EOF、空白、`/` 或 `>` 才算结束标签）；唯一例外是 JSON 数据块：首个 `type` 属性去除首尾 ASCII 空白、不区分大小写后恰为 `application/json` 或 `application/ld+json`。无/空 `type`、`module`、JavaScript 类型、`importmap`、`speculationrules`、未知类型、带 MIME 参数（如 `application/json; charset=utf-8`）仍算内联脚本；②③ 的来源规则对数据块同样适用；② 未闭合 `<script`；③ 非本地来源：`<script>` 的 `src`/`href`/`xlink:href`，`<iframe>`/`<frame>`/`<embed>` 的 `src`，`<object>` 的 `data`——以两个斜杠（`//`、`\\`、`/\`、`\/`，忽略前导空白与控制字符）开头，或在首个 `/`、`\`、`?`、`#` 之前出现 `:`（URL scheme，如 `http`/`https`/`data`/`blob`/`javascript`），或在首个 `?`、`#` 之前出现 `&`（字符引用可拼出上述任一形式），即视为非本地；④ `<base href>`、`<meta http-equiv=refresh>`、`<iframe srcdoc>`。外链样式表、`<a>` 与指向远程的 `<link rel=modulepreload>`（不执行）放行。保守的构建期检查：注释或 `<textarea>` 内的标记也会被当作标签，可能误拒 |
| `worker`（`.js`/`.mjs`） | 扫描 `new Worker(…)`、`new SharedWorker(…)`、`<expr>.serviceWorker.register(…)` 与 `new Worker(new URL("…", import.meta.url))`：首参为字符串字面量且按 HTML 同一条规则判为非本地时拒绝（退出 2）。首参为变量、拼接、含插值的模板等无法静态判定者计数，汇总为一行 warning，**不**使构建失败。这是 lint 不是沙箱——字面量内的转义不解码，正则字面量可能让扫描错位，刻意隐藏的远程 worker 逃得掉；它拦的是打包器实际产出的形状 |
| `--parent` 搭配非 patch kind | 拒绝（退出 2） |
| `--kind patch` 无 `--parent` | 拒绝（`E_PARENT`） |
| `--parent` | 可重复：base 在前，patch 依序在后。第一个必须是 base（否则退出 2）；其后每个必须是同 id 的 patch，且 `parent.version_code`、`parent.manifest_sha256` 指向前一个（否则退出 2）。链在内存中解析（依次应用 full/delete/delta）；不验签，故任一 entry 声明 `size` 或 `blob_size` > 64 MiB（桌面端 `MAX_ASSET_BYTES`）即拒绝（退出 2）；整条链累计解码字节（full 内容、delta 流、重建结果，含被后续 patch 替换的部分）上限 1 GiB，有声明大小的先扣预算，解码流在预算耗尽处中止，超出拒绝（退出 2）。每个 patch 都写全部文件，预算消耗约为 dist 大小 × 链长，链过长应发新 base 收拢。调用方只应传入自己发布或已 `tpk verify` 的包。新包的 `parent` 取自最后一个；其 id 必须与 `--id` 一致，`version_code` 必须 < 本包 |
| `--kind mod` | 清单 `policies.trusted = false`；其余 kind 为 `true` |
| 写出前 | 清单序列化后重新解析，客户端会拒绝的包在构建机失败 |

`min_shell` 的单一真相源是 `tpk pack --min-shell`（写入签名清单）。

条目生成（`--kind patch` 且有 `--parent` 时；其他 kind 只写 `full`）：

- 与解析后的 parent 链不同、且 `size ≥ --delta-threshold` 的文件尝试 bsdiff；delta 不划算则退回 `full`（§3.4）。
- 包级上限：delta entry ≤ 64 **且** delta 结果总字节 ≤ 32 MiB；超出部分退回 `full`，并提示 `N candidate(s) shipped as full`。
- 解析后的 parent 链有而 `dist` 无的路径写 `delete` 墓碑。
- 其余文件（含与 parent 链字节相同者）写 `full`。

确定性输出（同输入 ⇒ 字节相同，跨 OS）：

| 项 | 固定值 |
|---|---|
| entry / blob 顺序 | 按路径排序；ZIP 内先 `tpk-manifest.json`、`tpk-manifest.json.minisig`，再 blob |
| ZIP 方法 | `Stored` |
| blob 压缩 | zstd 固定 level 19；< 4096 字节不压缩 |
| mtime | DOS 纪元 `1980-01-01 00:00:00` |
| host system / 权限 | `Unix` / `0644`；无 extra field |
| 清单 | 固定字段顺序；`created_at` 由参数给定 |

确定性是 blacklist `sha256` 匹配与渠道清单 sha256 可复现的前提。

输出：`wrote / sha256 / size / entries N full, N delta, N delete`。

### 10.4 `tpk channel`

- 每个 pack 的 `id` / `kind` / `version` / `version_code` / `parent_version_code`（仅 patch）/ `size` / `sha256` 全部从包文件读出。
- `url = --url-base + 文件名`；`--url-base` 必须 `https://`，自动补尾 `/`。
- `optional = (kind == dlc)`；`--rollout`（默认 100，范围 1..=100）只施加到每个 `id` 中 `version_code` 最高的 pack，其余 pack 为 100（使新设备能拿到整条链）。
- `--watermark auto` ⇒ 当前 UTC `YYYYMMDDHHMM`；也可传显式数字。
- `--published-at` 缺省为 watermark 对应分钟的 RFC 3339。
- 每个 pack 条目的 `min_shell` / `max_shell` 从包签名清单抄写（包内未设则省略）。
- `--min-shell` 缺省取各包 `min_shell` 的最大值；`--force-shell` 显式给出才写。
- `--key-epoch` 默认 1，写入签名覆盖的 `key_epoch`。
- 写出前重新解析；写 `<out>` 与分离签名 `<out>.minisig`。
- `--notes` 原样写入清单；剥标记、丢弃可隐藏或重排文本的格式字符与截断到 200 个可见字符都发生在解析端（§11.1 第 5 条），因此客户端看到的可能短于传入值。

### 10.5 `tpk sign`

对任意文件写分离签名 `<file>.minisig`（trusted comment = `--trusted-comment` + 文件名）。包在 `pack` 时已内嵌签名，渠道清单由 `channel` 自带签名；`sign` 用于其他需单独签名的文件。

### 10.6 `tpk inspect`

不需要公钥、**不校验签名**；输出 `manifest_sha256`、签名是否存在（标注 NOT verified）、id/kind/version/version_code、parent、shell 范围、channel、created_at、trusted、entry 计数与解码后总字节。`--json` 打印完整清单。仅作调试，不得作为闸门。

### 10.7 `tpk verify`

- `--pubkey` 可重复；`--epoch` 若给出，数量必须与 `--pubkey` 相同（否则退出 3），缺省每把钥 epoch = 1。
- 按扩展名分派：`.tpk` 视为包，其余视为渠道清单（签名取 `<file>.minisig`）。
- 渠道清单：先解析，再按 §3.3 以清单内 `key_epoch` 验签，`--min-epoch` 作为下限。
- 包：接受由任一 `epoch ≥ --min-epoch` 的受信钥签名的包。
- 逐文件打印 `ok` / `FAIL`，任一失败退出 2 并报告失败计数。

## 11. 与官方 Updater 的协议

壳版本 = `package.version`（`tauri.conf.json`），SemVer。

客户端决策表：

| 条件 | 动作 |
|---|---|
| 渠道 `force_shell` 或 `min_shell` > 当前壳 | `check`/`download` 返回 `shell_required`，不应用任何 pack；升壳由宿主引导（桌面官方 updater、移动应用商店） |
| pack 的 `min_shell`/`max_shell` 不含当前壳 | 渠道条目带范围：plan 跳过该包（`ShellTooOld`/`ShellTooNew`），不下载；条目未带：stage 时 `download` 返回 `failed`（`E_SHELL`），不 stage、不拉黑 |
| 仅内容变化 | 只走 TPK |
| Rust 命令签名变化 | 升壳，可同时带新 seed base |

禁止 pack 内携带：

- 可执行文件、dylib/dll/so
- sidecar
- 改写 `$RESOURCE` 下的壳文件

下载器用插件内 `reqwest`，不要把 CDN 文件暴露给前端 `fetch` 后写入任意路径。

### 11.1 应用商店合规

以下为硬性约束（审核依据见 `docs/security.md` 与 `docs/app-review-checklist.md`）：

1. **App Store target 不得含 DLC / Mod**。`app-store` feature 打开时 `PackKind::Dlc` 与 `PackKind::Mod` 编译期不存在（feature 定义在 `tpk-format`，由 `tpk-resolve` / `tpk-store` / `tpk-client` / `tpk-cli` / `tauri-plugin-tpk` 转发）：包清单声明 `kind: dlc` 以 `E_POLICY` 拒绝；渠道清单中 `kind` 恰为 `dlc` 或 `mod` 的条目在反序列化时被丢弃而非整份失败（§4）；`tpk pack --kind` 不再接受 `dlc`/`mod`。内部 `__all` feature 专供 `--all-features` 扫到并抵消 `app-store`，各 crate 的 `build.rs` 把这对 feature 归一为 `cfg(app_store)`，否则整条 CI 矩阵会被静默切进 App Store 模式。JSON Schema 仍列出全部四种 kind——它描述的是线格式，与构建目标无关。
2. **移动端默认不自动更新**。移动端 `auto_check_on_launch` 与 `auto_download` 默认 `false`（§8.1）。
3. **移动端不注册 `tauri-plugin-updater`**。原生壳更新在移动端只走应用商店。
4. **不引导到商店外更新**。`shell_required` 只携带 `min_shell`，不得携带任何 URL；插件不自带任何 UI。
5. **`notes` 不是用户文案通道**。解析顺序固定：剥除标记（`<…>` 整段丢弃，未闭合的 `<` 吞掉其后全部内容，落单的 `>` 也丢弃；字符引用**不**解码，以免把刚删掉的标记还原）→ 丢弃能隐藏或重排文本的格式字符 → 控制字符成段折叠为单个空格 → trim → 截断为 200 个可见字符 → 结果为空则记为 `None`。规则是「丢掉能隐藏或重排文本的」，不是「丢掉一切不可见字符」：
   - **丢弃**：bidi 嵌入与覆盖 U+202A–U+202E、隔离符与已废弃的整形/数字控制 U+2066–U+206F、方向标记 U+200E/U+200F 与 U+061C、零宽空格 U+200B、软连字符 U+00AD、U+180E、BOM U+FEFF、行间注释 U+FFF9–U+FFFB、音乐格式控制 U+1D173–U+1D17A、tag 块 U+E0000–U+E007F。
   - **保留**：ZWNJ U+200C 与 ZWJ U+200D（波斯语/阿拉伯语整形与 emoji 序列依赖它们）、词连接符与不可见数学运算符 U+2060–U+2064、以及 U+0600–U+0605 等脚本专用 Cf 标记。它们塑形或影响断行，既不能重排也不能隐藏内容，丢掉等于损坏真实文案。

   文档标注仅供日志与诊断。
6. **包内不加载远程代码**。`tpk pack` 拒绝：非空内联 `<script>`（`application/json`、`application/ld+json` 数据块除外）；来源非本地的 `<script>`、`<iframe>`、`<frame>`、`<embed>`、`<object>`；`<base href>`、`<meta http-equiv=refresh>`、`<iframe srcdoc>`（规则见 §10.3）；`.js`/`.mjs` 中首参为非本地字符串字面量的 `Worker`/`SharedWorker`/`serviceWorker.register`。首参无法静态判定者只告警不拒绝——该检查是 lint 不是沙箱（§10.3）。
7. **Mod 永不经渠道下发**。plan 无条件跳过 `kind = mod`。
8. **备份排除**。`layers/` 排除出平台备份，失败只告警，不阻止启动。Apple 平台由 `tpk-backup` 设 `NSURLIsExcludedFromBackupKey`：在 `Store::open` 建出目录**之后**（标记设不到不存在的目录上，先设等于首启的层池仍进 iCloud），且每次 stage 成功后重设一次。该标记属于 URL 而非文件内容，Apple 只写明「该资源被排除出全部应用数据备份」，没有说明目录下此后新建的文件是否继承，实测报告也不一致——因此不假定继承：stage 是唯一往层池加文件的动作，重设一次只是一个 syscall，重复设置无害。`tauri-plugin-tpk` 保持 `#![forbid(unsafe_code)]`，唯一的 unsafe 调用独立在只针对 Apple 的叶子 crate `tpk-backup` 内（该 crate `#![deny(unsafe_code)]` + 单个 `#[allow]`），非 Apple 目标是零依赖的 no-op。`state.json` 刻意不排除（§5）。Android 仍由宿主在 `<data-extraction-rules>`（及 `backup_rules.xml`）中 exclude `tpk/layers`，插件无法合并宿主 manifest，片段见 `docs/disk-layout.md`。
9. **审核披露**。宿主必须在提审的 Notes for Review 中具体描述 OTA 机制，并使其可供审核复现。
10. **不支持 isolation 模式**。isolation 模式依赖编译期注入 `index.html` 的 hook，OTA 替换 HTML 后无法保证成立。`attach()` 检测到该模式时打一条 `log::warn!`（§13.2）。

## 12. 安全模型

信任根：嵌入壳内的 `pubkeys[{key, epoch}]` + 持久化的 `min_key_epoch`。

威胁与对策：

| 威胁 | 对策 |
|---|---|
| 篡改 CDN | 渠道清单与包清单 minisign；整包 sha256；per-blob `blob_sha256` + 解码后 `sha256` |
| 重放旧清单 | 按渠道持久化 watermark，拒绝严格更小 |
| 渠道清单验签失败 | 返回错误由调用方重试，不写 blacklist（CDN 瞬时不一致不得永久禁掉好包） |
| XSS 改更新源 | URL/公钥仅原生配置；URL 模板只允许 4 个变量且展开后必须 https |
| 半写入包 / 状态 | 下载写 `tmp/*.part`，size + sha256 校验后在缓存根内 rename 定稿，stage 以原子写（fsync）写入层池；临时文件 → fsync → rename → fsync 目录；启动时整文件 sha256 核对层（元数据比对〔未实现〕） |
| 坏包白屏 | booting 修订第 3 次冷启动仍未确认 → 回滚 + condemn；连续 3 次回滚 → degraded |
| blacklist 被重打包绕过 | `(id, version_code)` 与 `sha256` 双键匹配；`tpk pack` 确定性输出 |
| zstd 炸弹 | 解码上限（§3.4）；bspatch 精确预分配 + 单资源上限 |
| Zip slip / 夹带 | 规范化路径，拒绝 `..`；条目名白名单、无重复名、无未引用 blob |
| 模组覆盖登录页 | 〔未实现〕`mod_protected_globs`。现状：mod 层一律拒绝加载，渠道永不下发 mod |
| 降级攻击 | `version_code` 单调：相等即「已经装着」而拒绝；更旧则撞上按 `id` 持久化的 `version_floor`（commit 时抬升、永不下降），它比被 condemn 的层活得久，也比 `reset` 活得久 |
| 密钥泄漏 | 以更高 epoch 的新钥签名并在渠道清单写入新 `key_epoch`，客户端下限抬升后旧钥处处被拒。持泄漏旧钥者无法签出更高 epoch 的清单，只能推高自己出局。撤销生效时间 = 含新钥的壳渗透时间 + `key_epoch` 传播时间 |

降级下限的唯一豁免：`reset` 之后 `seed_if_absent`（§5）会把随包分发的 seed 内容直接提交为 committed，即使其 `version_code` 低于 `version_floor`。这是有意的——那一刻没有任何 committed 修订，拒绝 seed 只会把设备留在 embedded 资源上，而那本来就是同一份随包内容，挡住它不提高任何安全性。渠道下发的一切仍受下限约束，下一次成功的 check 会把设备带回更高的版本。

Mods〔未实现〕：`trusted = false`，默认不能覆盖受保护 glob；即使启用也不走 CDN 自动装包。

## 13. 运行时接入（代码契约）

```rust
pub fn run() {
    let mut ctx = tauri::generate_context!();
    let tpk = tauri_plugin_tpk::attach(&mut ctx);
    tauri::Builder::default()
        .plugin(tauri_plugin_tpk::init(tpk))
        .run(ctx)
        .expect("error running app");
}
```

公开入口：

```rust
pub fn attach<R: Runtime>(context: &mut tauri::Context<R>) -> TpkHandle;
pub fn init<R: Runtime>(handle: TpkHandle) -> TauriPlugin<R, Option<TpkConfig>>;
pub fn init_with_config<R: Runtime>(handle: TpkHandle, config: TpkConfig)
    -> TauriPlugin<R, Option<TpkConfig>>;
```

- 插件名 `tpk`，与 ACL 命名空间一致。
- 桌面可并列注册 `tauri-plugin-updater`（升壳走官方 updater，§11）；**移动端不得注册**（§11.1）。

### 13.1 时序

```
generate_context!()
  └─ attach(&mut ctx)          换 Assets，不解析路径、不做 IO
Builder::build()
  └─ 插件 setup                 状态机、索引，全部在此；此时尚无窗口
App::run()
  └─ 创建窗口                    WebView 开始请求资源，读到已冻结的索引
```

### 13.2 `attach`

1. 从 `ctx` 取出当前 embedded `Assets`
2. 构造 `PackAssets { fallback: embedded, shared: Arc<Shared> }`，`Shared` 内为空的 `OnceLock<Arc<Resolver>>`
3. 装回 `ctx`，返回持有同一 `Arc<Shared>` 的 `TpkHandle`

`attach` **不解析任何路径、不打开任何文件**：Android 的 `app_local_data_dir()` 经 JNI，此时不可用。

检测到 isolation 模式时打一条 `log::warn!`（§11.1），`attach` 仍不会失败。判定取自 `context.config().app.security.pattern` 是否为 `PatternKind::Isolation`——`tauri::Pattern::Isolation` 这个变体藏在 tauri 的 `isolation` feature 后面，此处无法匹配。

### 13.3 插件 `setup`

在 `Builder::build()` 末尾、任何窗口创建之前执行。顺序：

1. 取配置：`init_with_config` 传入的优先，否则 `plugins.tpk`；无配置 → 放弃本次 OTA
2. `enabled = false` → 结束，只服务 embedded
3. 构造 TrustStore；解析壳版本（`package.version` 须为 SemVer）
4. 用 `app.path()` 解析两根：`$APPLOCALDATA/tpk/`、`$APPCACHE/tpk/`（§5）
5. `Store::open`（其中建出目录）；随后对 `layers/` 请求备份排除——必须在建目录之后（§11.1）
6. 配置了 `seed_dir` 且无 committed 修订：装入 seed，直接 committed；失败只告警
7. `Store::boot()`（§7）；有回滚则记日志，并记入 `status().rolled_back`（不发事件：此时尚无窗口）
8. 按 boot 结果构建 Resolver（§6.3）；加载失败的层记入 `failed_layers`，并按失败码记 strike（`E_SHELL`、`E_SIGNATURE`、mod 层被拒、层栈已满除外，§6.3）
9. 若活动修订有层：起后台线程，检查并重建缺失的 delta 物化结果（§6.5）；不阻塞 setup
10. `Shared.set_resolver(resolver)`——一次装入，进程内不再替换
11. 检查 embedded 是否有 `index.html`（`has_embedded_fallback`），扫描主窗口危险 capability
12. `app.manage(TpkState)`
13. `auto_check_on_launch = true` 时起一个任务执行启动自动更新（§8.1）；只在状态注册之后，因而插件未启用或第 4–7 步已放弃 OTA 时它什么都不做，也不阻塞 `Builder::build`

**`setup` 永不返回 `Err`**：返回 Err 会让 `Builder::build` 失败、应用起不来。任一步失败只 `log::error` 并放弃本次启动的 OTA；Resolver 未装入时 `PackAssets` 全部由 embedded 应答。

〔未实现〕setup 同步阻塞预算与 `max_boot_blocking_ms`（§18）。

### 13.4 `PackAssets`

- 层集合进程生命周期内冻结（§7），故用 `OnceLock<Arc<Resolver>>` 而非锁：运行中的 WebView 始终看到同一份索引。
- `get(key)`：依次尝试 `key`、`key.html`、`key/index.html`。overlay 命中 → 返回；墓碑 → 返回 `None`，**不回落 embedded**；未命中、层损坏或物化结果缺失 → 下一候选；全部未命中 → embedded（§6.4）。
- 路径规范化失败（`..` 等）→ overlay 视为未命中。
- `iter()`：overlay 与 embedded 的并集，overlay 优先。
- `csp_hashes(html)`：§6.8。
- Resolver 未装入（`attach` 之后、setup 之前，或 setup 放弃 OTA）时，三个方法全部委托 embedded。

### 13.5 开发模式

- 桌面存在 `devUrl` 时 WebView 直连 dev server；`PackAssets` 仍在，供 `AssetResolver` 与 Rust 读取。
- 移动端 `ios dev` / `android dev` 把全部资源请求代理到 dev server，`Assets::get` 从不被调用。验证 OTA 用 `ios build --debug` / `android build --debug`。
- 〔未实现〕`TPK_DEV_LAYERS` 指向本地 tpk 作为层。

## 15. 错误码（冻结）

```
E_DISABLED
E_NETWORK
E_SIGNATURE
E_HASH
E_SPEC
E_PATH
E_PARENT
E_SHELL
E_WATERMARK
E_BLACKLIST
E_IO
E_DELTA
E_STATE
E_POLICY
```

映射：

- store 完整性失败（含清单 `id`/`version_code` 与渠道条目不一致）→ `E_HASH`
- stage 时包壳范围不含当前壳 → `E_SHELL`（不写黑名单）
- stage 时 patch 的 parent 链与其下同 id 层不符，或其下没有同 id 层 → `E_PARENT`（§3.3；不写黑名单）。「其下没有同 id 层」区分两种原因：从未安装，或装过但已被 blacklist 拒绝——对合并是一回事，对读日志的人不是
- 非默认策略 glob → `E_POLICY`
- 渠道清单 watermark 过旧 → `E_WATERMARK`
- stage 时被黑名单拦截 → `E_BLACKLIST`
- 插件未初始化 → `E_STATE`；配置错误、模板错误、`set_mod_enabled`（插件启用时）→ `E_SPEC`
- `enabled = false` 或 setup 放弃 OTA 时的 `status`/`reset`/`set_mod_enabled` → `E_DISABLED`（§9.1）
- blacklist reason 对应关系见 §5

日志不打印完整 URL query 中的令牌。

## 16. 测试矩阵（必须与实现一起交）

格式：

- 规范化路径拒绝用例
- 重复 path / 未知 op / 坏 spec
- 非默认 policies 被拒
- blob 名与 `blob_sha256` 不符、`blob_size` 不符被拒
- zstd 解码超限被拒
- tombstone 遮蔽下层 full
- 高层 full 覆盖下层 delete
- delta 基哈希不匹配
- 签名错误 / 截断 ZIP
- JSON Schema 对拍：三份 schema 与解析器互钉；`state.json` 以 store 实际写出的字节校验 `store-state.schema.json`

签名：

- 新 epoch 钥签的包在旧下限下可 stage
- 低于下限的钥处处被拒
- 渠道清单声明的 `key_epoch` 与签名钥 epoch 不一致被拒

状态机：

- staged 后杀进程，再启动进入 booting
- booting 未确认时前两次启动重试、不拉黑；第 3 次冷启动回滚并立即拉黑
- 回滚只 condemn 不属于 committed 的层
- 连续 3 次回滚进入 degraded；成功确认后清零
- notify_ready 后杀进程，层保持 committed
- reset 保留 install_id / watermark / key epoch
- stage 继承活动修订的层；非 patch 替换同 id 全部层
- stage 时物化 delta；base 哈希不符 stage 失败
- 壳范围不符 stage 失败
- 物化结果被清后回退 embedded 且不计 strike、后台补齐
- 损坏的物化结果文件被删除后重建
- gc 保留进行中的临时文件、删除过期临时文件

黑名单：

- 重打包同一 `(id, version_code)` 不可绕过
- 瞬态条目三振生效、TTL 过期
- condemn 立即生效

客户端：

- watermark 回退被拒；相等被接受
- stable → beta → stable 不被卡死
- rollout 分桶稳定，且每个版本重洗；桶外仍推进 watermark
- min_shell 拦截
- 已装 base 时只下 patch
- 磁盘满时 staged 不切换指针

CLI：

- `tpk pack` 输出确定性
- 拒内联 script、拒远程 script/iframe、拒无扩展名文件

集成：

- 替换 index.html 后 origin 仍是 tauri://，localStorage 仍在
- overlay 接管 HTML 时不注入 embedded 内联脚本 hash；overlay 的 `.js`/`.mjs` 内容 hash 被注入
- 官方 updater 与 TPK 同时配置不抢 Assets

### 17.3 内容发布（`content-release.yml`，应用侧模板）

手动触发，输入 `channel`、`version`、`kind`（patch/base）、`rollout`、`released_shell`（可选）、`dry_run`。同一 channel 串行。需应用侧配置 `CDN_BASE` / `CDN_BUCKET` / `AWS_REGION` / `TPK_PUBKEY` / `TPK_KEY_EPOCH` 变量与 `TPK_SIGNING_KEY` / AWS secrets。

```
cargo install tpk-cli
  → identity: version_code = UTC YYYYMMDDHHMMSS；created_at = UTC RFC 3339（钉住，保确定性）
  → 校验输入：version 为 SemVer、rollout 为 1..=100 整数、released_shell 非空时必须是严格 MAJOR.MINOR.PATCH
    （不带预发布与 build metadata，因为断言用 sort -V 比较，它把预发布排在正式版之上）；
    所有 inputs 经 env 传入脚本，不在 run 中直接展开 ${{ }}
  → 构建前端 → dist/
  → 拉取已发布 {channel}/latest.json（404 时 patch 失败、base 视为首发）；按 version_code 升序下载要保留的 pack：
      其他 id：全部保留
      同 id：保留最新 base 及其后（version_code ≥ 最新 base）的 pack，更早的丢弃；[patch] 这些即 --parent 链
      [base 且 rollout = 100] 同 id 全部丢弃；[base 且 rollout < 100] 保留同 id 当前链，桶外设备（含新装）仍能收敛到旧链
    每个 pack sha256 与清单比对，再 tpk verify --min-epoch $TPK_KEY_EPOCH
  → tpk pack --kind --id --version --version-code --created-at --channel --dist [patch：同 id 链逐个 --parent]
  → tpk channel --pack <保留的 pack> --pack <新包> --url-base $CDN_BASE/{channel}/ --watermark auto
                --key-epoch $TPK_KEY_EPOCH --rollout（只作用于各 id 最新 pack）→ latest.json + .minisig
  → tpk verify --pubkey $TPK_PUBKEY --min-epoch $TPK_KEY_EPOCH + tpk inspect
  → [patch] watermark 必须严格大于上一份 latest.json
  → [released_shell 非空] 断言渠道 min_shell 与每个 pack 条目的 min_shell 均 ≤ released_shell；留空则跳过并打印一行说明
  → 上传（非 dry_run）：先 .tpk（immutable, 长缓存）→ 等待 → {watermark}.json 与 .minisig（immutable, 长缓存）
    → latest.json 与 .minisig（短缓存）
  → 冒烟：经 CDN 取回 latest.json(+sig) 与该 id 中 version_code 最高的 pack，tpk verify，watermark 与刚上传一致；
    再取回 {watermark}.json 与上传的 latest.json 逐字节 diff
  → 冷备份：GitHub Release `content-{channel}-{version_code}` 附 .tpk / latest.json / .minisig
```

每次发布同时上传不可变副本 `{channel}/{watermark}.json` 与 `.minisig`（回滚与审计用），字节与 latest.json 相同，故同一份分离签名即可覆盖。它**先于** latest.json 上传，所以看见新 latest.json 的设备一定能取到对应的钉死副本；watermark 从生成好的清单里用 `jq` 读回，不在流水线里重算时间戳。同名对象已存在即判定为异常并让 job 失败——重写它等于改写设备已经见过的内容。

发布前断言包与渠道的 `min_shell` ≤ 已发布的壳版本（`released_shell` 输入）；否则旧壳收到 `shell_required`（渠道级）或该包被 plan 跳过（包级），内容更新到达不了这批用户。不追踪已发布壳版本的仓库把该输入留空，断言跳过。

壳更新走官方 updater 与应用自身的商店 / updater 流水线，不在本工作流内；**内容 pack 与平台无关，只发一份**，不得塞进 per-arch updater json。

### 17.4 版本号纪律

| 对象 | 规则 |
|---|---|
| 壳 | `x.y.z`（Cargo + tauri.conf + package.json 同步）；客户端取 `package_info().version` |
| 包 `version_code` | 每 `id` 单调递增、永不复用；使用 UTC `YYYYMMDDHHMMSS`。不得用 CI 构建号（迁仓库、重建 workflow 会重置，客户端的单调检查随即永久拒绝新内容） |
| 包 `min_shell` | 唯一来源 `tpk pack --min-shell`（签名清单内）；渠道级 `min_shell` 缺省取各包最大值 |
| 渠道 `watermark` | `tpk channel --watermark auto` = UTC `YYYYMMDDHHMM`；只增不减；客户端拒绝严格更小、接受相等。每次发布另存不可变副本 `{channel}/{watermark}.json`，同名对象已存在即发布失败（§17.3） |
| `key_epoch` | 与 `plugins.tpk.pubkeys[].epoch` 对应；`verify --min-epoch` 设为客户端已达下限 |

### 17.5 回滚与强制升壳

- 不存在「退回旧版本」：客户端两道门都要过——`version_code` 必须 `>` 已安装值（相等即已经装着），且不得 `<` 该 `id` 的 `version_floor`（§5，曾经 commit 过的最高版本，`reset` 与 condemn 都不会把它清零）。回滚 = 把旧内容以**更高的** `version_code` 重新发布，且发 `base` 而非 `patch`（线上同时存在两个 cohort，patch 的 parent 只能指向其一）。
- 回滚实际生效时间 = 用户下一次冷启动（进程内不切层）；移动端因无自动检查，还要加上用户主动触发的时间。
- 灰度：同一内容重发 `tpk channel --rollout 10 → 50 → 100`；分桶按设备与 `(id, version_code)` 确定，扩大比例为超集。
- `--force-shell` 让内容通道对低于该版本的壳彻底停摆，包括热修复。仅在希望这批用户连热修复都拿不到时使用。

## 18. 性能预算

| 项 | 目标 | 状态 |
|---|---|---|
| setup 内同步阻塞总时长 | 桌面 ≤ 200 ms；移动 ≤ 100 ms | 〔未实现〕无预算执行，未测量 |
| 冷启动索引加载 | ≤ 30 ms（≤ 2000 entry/层，≤ 3 层）；耗时与资源总字节数无关（O(entry)，不得 O(bytes)） | 〔未实现〕当前每层整文件 sha256；未测量 |
| 缓存命中路径 | 字节拷贝不多于一次 | 插件内命中返回 `Arc`，交给 Tauri 前一次拷贝；无测试门禁 |
| 首屏全部子资源解析 | 总耗时 ≤ 100 ms，并发请求不得完全串行 | 〔未实现〕未测量；当前同层读取互斥（§6.7） |
| 索引常驻内存 | ≤ 200 B / entry / 层 | 〔未实现〕未测量；当前每层常驻容器读取器与清单 |
| 首次 seed 复制 | 仅首次安装 | 已实现 |
| 下载 | 断点续传 `.part`，size + sha256 校验后在缓存根内 rename 定稿，stage 时原子写入层池 | 已实现 |

约束：

- 层完整性在 `stage()` 时校验一次；〔未实现〕启动只比对元数据。运行时防线是清单签名 + per-blob 读取时校验（`blob_size`、`blob_sha256`、解码后 `sha256`），后置 sha256 校验必须保留。
- delta 物化不进入 `boot()`/setup 同步路径（§6.5）。
- 〔未实现〕建索引后丢弃 `ZipArchive`，以 `read_at`/`seek_read` 无锁读取。
- bspatch 输出按 `entry.size` 精确预分配。

|---|---|---|---|
